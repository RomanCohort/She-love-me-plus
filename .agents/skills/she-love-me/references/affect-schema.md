# affect 段 schema（情感计算层）

`data/stats.json` 里的 `affect` 段是**公开接口**。一旦发出去，改字段名或改嵌套结构
会断掉所有下游消费方。所以这份文档先于代码存在，代码照它写，不是反过来。

**当前版本：`1.0.0`**

---

## 契约（最重要的一条）

**`affect` 这个 key 永远存在，不可用时也只是 `status` 不等于 `ok`，不会是缺键。**

消费方看 `status`，不看 key 在不在。所有降级路径都必须 **`exit 0`**——
`stats_analyzer.py` 遇到任何情感层问题都不得中断主分析。

```python
affect = stats.get("affect", {})
if affect.get("status") == "ok":
    ...   # 用
else:
    ...   # 跳过，或显示「情感层未启用」+ affect.get("reason")
```

**这个模式适用于所有消费 `stats.json` 的代码。** 直接写
`stats["affect"]["per_speaker"]` 会在 `disabled` 时抛 `KeyError`。

---

## status 三态与降级表

| 条件 | status | reason 示例 | 行为 |
|------|--------|-------------|------|
| `--affect off`（默认） | `disabled` | `未启用（--affect off）` | 不算 |
| onnxruntime 未安装 | `disabled` | `缺少可选依赖：…` | 不算，exit 0 |
| 本地无模型缓存且 `--no-download` | `disabled` | `本地无模型缓存（…），且指定了 --no-download` | 不算，exit 0 |
| 文字消息 < 50 条 | `disabled` | `文字消息不足 50 条（实际 N）` | 不算，exit 0 |
| 模型下载失败 / 加载失败 | `degraded` | `模型加载失败：…` | 不算，exit 0 |
| 正常 | `ok` | `null` | 计算并写入 |

**`disabled` = 一开始就没打算算；`degraded` = 试了但没成。** 消费方对两者的处理
可以相同；区分它们是为了诊断——`degraded` 意味着环境本来是可以的，值得看一眼。

## 字段

以下是 `status == "ok"` 时的完整形状（数值取自一份真实语料，仅作形状说明）：

```json
{
  "affect": {
    "version": "1.0.0",
    "status": "ok",
    "reason": null,
    "model": "onnx-community/bge-small-zh-v1.5-ONNX",
    "anchors": { "valence_pairs": 10, "arousal_pairs": 6 },
    "per_speaker": {
      "me":   { "messages": 622, "valence_mean": -0.006, "valence_std": 0.0832,
                "arousal_mean": 0.0149, "arousal_std": 0.0664 },
      "them": { "messages": 483, "valence_mean": -0.0037, "valence_std": 0.0985,
                "arousal_mean": 0.0104, "arousal_std": 0.0723 }
    },
    "within_between": {
      "me_to_them": { "within_r": 0.136, "between_r": 0.329, "n": 296,
                      "n_conversations": 29, "ci95_cluster": [0.068, 0.267] },
      "them_to_me": { "within_r": -0.014, "between_r": 0.148, "n": 287,
                      "n_conversations": 28, "ci95_cluster": [-0.097, 0.145] }
    },
    "interpretation": {
      "within": "…", "between": "…", "warning": "…"
    },
    "orthogonalisation": {
      "applied": false,
      "residual_norm": null,
      "reason": "within_between 只用效价投影，不涉及嵌入余弦，无泄漏通道"
    },
    "axis_diagnostic": { "axis_correlation": -0.13, "verdict": "OK，接近正交" },
    "coverage": {
      "messages": 1105, "span_days": 182,
      "days_any_message": 30, "days_both_senders": 27, "note": "…"
    },
    "carryover": {
      "me":   { "r": 0.029, "n": 295, "ci95": [-0.086, 0.143] },
      "them": { "r": 0.098, "n": 174, "ci95": [-0.051, 0.243] }
    },
    "negative_results": ["daily_timeseries", "semantic_nearest_neighbour",
                         "mediation", "moderation"],
    "degraded_reason": null
  }
}
```

`status != "ok"` 时，除 `version` / `status` / `reason` / `model` / `anchors` /
`negative_results` 外的字段**一律为 `null`**。

### `version`
语义化版本。**以下任一变化都要 bump**，因为跨版本的数字不可比：

- 换句向量模型或模型精度档
- 改 `affect_anchors.py` 的锚句（轴的定义变了）
- 改中心化 / 标准化方式
- 改进 `orthogonalise()` 的算法

### `status` / `reason`
见上表。`reason` 仅在 `status != "ok"` 时非空。

### `per_speaker`
键固定为 `"me"` / `"them"`——与 `messages.json` 的 `sender` 字段一致。
**不要用 `her` / `him`**：本 skill 是通用的，联系人性别不是已知量。

`valence_mean` / `valence_std` 是逐条消息投影后的均值与标准差；`arousal_*` 同理。
均为原始投影值（未经标准化），落在 `[-1, 1]`。

### `within_between`
**这是本段最容易被误读的地方，消费方必须读 `interpretation`。**

- `within_r`：**会话内**相关。同一段对话里，一方偏离本段均值时另一方跟不跟。
  **只有这一项可以解释为「回合级跟随」。**
- `between_r`：**会话间**相关。不同对话之间整体效价的相关。**不得解释为情绪传递**——
  它反映的是对话整体氛围差异（有些对话两边都更正向），把两边一起抬高，
  其中不含任何一方的跟随。
- `ci95_cluster`：按会话整块重抽的 bootstrap 置信区间。**判定显著性看它**，
  不要用按独立样本算的区间（回合对不独立）。

`between_r` 的数值通常比 `within_r` 大（实测 0.329 vs 0.136）。**只报一个数时必须报
`within_r`**；单独出现 `between_r` 极易被读成「跟得更紧」，那是误读。

### `anchors`
效价轴 / 唤醒轴各由多少对锚句定义。**改锚句必须 bump `version`**——轴的定义变了，
数字就不可跨版本比。

### `axis_diagnostic`
测量有效性自检。`axis_correlation` 是效价轴与唤醒轴的点积（唤醒锚句正负配平后
应接近正交）；`verdict` 是中文判读。

**`|axis_correlation|` 逼近 1 说明唤醒轴退化成第二个效价轴**，此时所有基于唤醒的
结论都不成立。

### `coverage`
数据密度，**用来解释「为什么没给时间序列指标」**。
`days_both_senders` 是两方当天都有消息的天数——实测这类闲聊语料里它可能极低
（182 天里只有 27 天）。这个字段的存在是为了让人一眼看到密度约束，
而不是把缺失的指标当成漏做。

### `carryover`
自我情绪延续（self-contagion）：同一人连着两条消息之间效价的相关。

`ci95` 是**朴素** Fisher 区间，未做聚类校正。对**零结果**而言这是偏保守的方向
（校正只会撑宽区间、让它更不显著）；但若这里跑出显著结果，必须先补聚类校正再信。

### `daily_valence`（v1.2.0 新增）

逐日效价均值，**覆盖从第一天到最后一天的每一个日期**，没消息的天为 `null`：

```json
"daily_valence": [
  {"date": "2026-03-24", "me": 0.0053,  "them": 0.0100},
  {"date": "2026-03-25", "me": -0.0100, "them": 0.0746},
  {"date": "2026-03-26", "me": null,    "them": null}
]
```

**为什么把空白日也列出来（不是只列有消息的日子）**：报告画的是折线图，横轴按**索引**均匀排。只列「有消息的日子」的话，182 天里那 68 天空洞会被压成图上一小步——**看着像「一直在聊」，把最该看见的断层藏起来**。补上空白日后，那段空洞占掉大半个横轴，一眼就看得见。

实测这份语料：182 个点里**有 153 天双方都没消息**。这个比例本身就是信息。

**给报告用时的规矩：只画这条走势，不画 `within_r` / `between_r`。** 那个相关系数是给分析者的；报告读者拿到只会误读（`between` 数值更大，极易被读成「跟得更紧」）。

### `semantics`（v1.1.0 新增，可选子对象）

**语义特征层。定位：不下结论，只给 LLM 读原文时的辅助坐标。**

本项目的最终分析是 LLM 做的。这一层的职责不是产出结论，而是把「嗯/哦/好 出现 47 次」
换成「这段时间的情绪坐标、话题主导性、关心表达强度」。门槛低得多，也是它真正的用途。

| 子键 | 内容 |
|------|------|
| `axis_diagnostic` | 各语义轴的**正交化前**相关矩阵 + 冻结顺序。**看 `before`**，它才是有信息量的那个 |
| `care_intensity` | 关心轴（关心表达 ↔ 事务处理）每人均值/标准差 |
| `topic_dominance` | 与所在对话窗口质心的距离，每人均值 |
| `attachment_hint` | 依恋-焦虑 / 依恋-回避两维（**已扣掉效价与唤醒**） |
| `axis_exemplars` | **本层最重要的产出**——每条轴上最靠前的若干条消息**原文** |

#### 读 `semantics` 时的三条硬规矩

**1. 看 `axis_exemplars`，别看均值。** 622 条消息取平均会把真正体现轴向的少数句子
稀释掉——实测关心轴 我 -0.0212 / 她 -0.0306，**差 0.009**，LLM 拿着这个数什么也做不了。
但「这条轴上最靠前的 8 条是这些原句」是能直接读、直接判断的。**给的是原文不是分数**，
因为极值也是噪声最大的地方，要让 LLM 看到句子本身再判断。

**2. `attachment_hint` 不是诊断。** 它**没有外部效标**——效价轴至少有表面效度可以眼看
（「恭喜恭喜」落在最正端），「焦虑轴 0.34」我们没有任何办法知道它是不是真的对应焦虑。
而且正交化后它的含义是「**扣掉说得正面/负面之后**剩余的焦虑措辞倾向」（原始焦虑轴与
效价轴 r = **-0.445**，不扣的话「焦虑型分数高」有一大块只是「说得比较负面」）。
**只能当提示方向**；按项目铁律「无证据不诊断」，任何依恋结论必须回到原文引用具体句子。

**3. `topic_dominance` 是双向的。** 距离大既可能是「把话题拉向新方向」，也可能是
「说跑题了」或「发了个表情包」——两者在数值上同号，必须回原文分辨。

#### 关于「用语义替代冷淡词表」——**已证不成立，且方向相反**

**别再试。** 三次尝试全部失败，最后一次做了人工逐条判定（带上文，106 条）：

| 方案 | 实测结果 |
|------|---------|
| 低效价窗口 | 11 条真敷衍的效价**全部为正**（+0.035 ~ +0.118）；而效价最低的一批（-0.173 ~ -0.060）是「没事」「不行」「别急」「咳咳」——**有情绪内容，反而不是敷衍** |
| 低唤醒 | 单个例子（「嗯」a=-0.054 vs「嗯嗯我超级想去！」a=+0.160）有效，**全组重叠**；「可以的！」a=-0.058 落在敷衍侧 |
| 信息量（`novelty`） | 敷衍 0.6177 vs 短但不敷衍 0.6070，**差 -0.0107** |

**「效价 < 0 判冷淡」这条规则的实测成绩：召回 0/11 = 0%，精确 0/14 ≈ 0%。**
它一条真敷衍都抓不到，抓到全是有情绪内容的消息。

**为什么是反的**：真敷衍（嗯/哦/好）是**温和的应答**，没有负面内容，投影偏正；
低效价那批承载了真实的情绪。所以这条规则会把「**对方在低落**」判成「**对方在敷衍**」
——这两个在关系分析里是相反的结论。

**根因**：敷衍是**语用**现象——它表达「我不想投入这段对话」，是**关系信号**。
情绪模型测心情，信息量测内容，敷衍测的是「这句话在关系里干什么」。三个空间都不是它待的地方。

**语境决定一切，这点已被数据证实。** 同一句「加油」：

```
我: 从现在开始苦练摄影📸      她: 加油   ← 语境里是关心
我: 明天六级加油！            她: 加油   ← 仍是关心
```

孤立看这两个字，效价 +0.110、白名单不收——两种做法都对，因为「它是不是敷衍」
这个问题**只有上文能回答**。任何脱离上下文的单句判定（无论词表还是模型）都不成立。

**长度看似有效，但分不开**：真敷衍长度均值 1.5、被误判者 1.7，差 0.2 字。纯长度规则
命中 106 条、假阳性 95 条（**90%**）；现行白名单命中 11 条、假阳性 **0**。

**结论：冷淡检测留在 `lexicon.DISMISSIVE_REPLIES` 白名单里。** 中文的敷衍是一小撮
约定俗成的封闭词（嗯/哦/好/行），约定俗成的东西穷举就是对的。

**连带结论——别的「单句分类」也别指望模型**：凡是判定依赖上下文的语用标签
（敷衍、试探、求和、推开），单句投影都做不了。要做只能做**带上下文的窗口级**判定，
而且必须有可核验的人工标注才能声称有效。

### `orthogonalisation`
`applied`：是否对嵌入做了情感方向正交化。`residual_norm`：正交化后残差与效价轴的
最大点积（应 ≈ 0）。`reason`：说明为什么 applied 是当前这个值。

`applied: false` 有两种情况，看 `reason` 区分：① 该路径本来就不涉及嵌入余弦
（`within_between` 就是），没有泄漏通道；② 漏做了（**这是 bug**，不应出现）。

**注意**：Gram-Schmidt 只保证**数值正交**（<1e-7），不保证语义正交。残差子空间里
仍可能存在其它与情绪相关的方向。所以正交化之后残存的相关只能读作「来源不明」，
不能读作「去掉泄漏后仍有真效应」。详见 `scripts/affect.py: orthogonalise()`。

### `negative_results`
**已知在这类数据上走不通的分析路径。** 报告生成器可以直接引用，不必硬编码。

| 值 | 含义 |
|----|------|
| `daily_timeseries` | 日粒度时间序列。闲聊语料天生稀疏（实测 182 天里仅 27 天双方有消息），时滞相关在 lag=±5 时样本只剩 6 个点，结果全是噪声 |
| `semantic_nearest_neighbour` | 语义近邻检索。跨天、字面不同、语义相同的消息对在自然对话语料中极稀疏（实测阈值 0.70 时全语料仅 3 对） |
| `mediation` | 中介分析。三消息链在选择变量上做了条件（选择偏差），同期版本 M 与 Y 共享文本载体（测量共享方差） |
| `moderation` | 调节分析。连续性指标与效价共享嵌入几何，正交化后仅剩边缘效应且过不了多重比较校正 |
| `sarcasm_recall` | 讽刺候选召回（原 Phase 4b，用 440MB 外部模型）。**已删除，不要再加回来**：① 讽刺是语用现象，与「敷衍」同类——单句/邻域极性对比的判据在任何话题转换处都会成立；② 它没有可验证路径（1105 条日常闲聊里讽刺是个位数，标不出来）；③ **讽刺检测是 LLM 读原文本来就更擅长的事**，给 LLM 一个粗筛结果不如让它自己读 |

> 上述每一条的完整实验记录见 `affect-limits.md`。**加新模型或新指标之前先读那一份**——
> 那里面记的都是撞过墙的路。

### `degraded_reason`
当 `status == "ok"` 但内部有非致命问题时非空。正常情况下为 `null`。
（与 `reason` 的区别：`reason` 解释**为什么整个段没算**，`degraded_reason` 解释
**算出来了但哪一步打了折扣**。）

---

## 兼容性规则

1. **只增不改。** 新字段可以加（消费方应忽略不认识的键）；已有字段的**名字和类型**
   不得变更。确需变更时 bump 主版本号，且消费方要按 `version` 分支处理。
2. **`status != "ok"` 时，除 `version` / `status` / `reason` / `model` /
   `negative_results` 外的字段一律为 `null`。** 消费方不要假设它们在。
3. **`per_speaker` / `within_between` 的键是固定的**，不要按数据动态增减——
   缺某一方时该键为 `null`，不是消失。
