# 对话动作受控词表（情绪 / 意图 / 时刻）

本文件定义「她不一样」的**逐条对话动作层**词表，供两个消费方共用：

| 消费方 | 位置 | 用到的部分 |
|--------|------|-----------|
| 实时标注层 | `data/live/annotations/*.json` 的 `per_message[].emotion.label` / `.intent.label` / `probs` 键 / `key_moments[].kind` | 全部 |
| 批量分析层 | `analysis.json` 的 `intent_profile` / `language_patterns.emotion_distribution` / `moments[].kind` | 全部 |

> **来源与许可**：12 情绪、36 意图、12 时刻 kind 三套词表移植自
> [Reverie0123/crush-monitor-universal](https://github.com/Reverie0123/crush-monitor-universal)
> （MIT License，Copyright © 2026 Crush Monitor contributors），其表结构与
> criteria 原文取自 `shared/labels.ts` / `shared/intents.ts` / `shared/memory.ts`。
> 本文档按本项目框架改写：**新增 F5 前置纪律、与 `symmetry_score` 的分工、
> 以及「量化不可得」的处理方式**，其余保持原样。

---

## 唯一最重要的一条

**词表是推荐值域，不是硬校验。**

这是 `live-annotation-schema.md` 读侧容错哲学的直接延续：消费方**必须容忍词表外的值**，
不得因为见到陌生标签就报错或丢弃整条记录。渲染器遇到词表外的值时走灰色兜底
（`enum_key()` 返回 `None` → `#6b7280`）。

同理，**`unknown` / `other` / `难判断` 是合法且常用的值**，不是失败。宁可标 `unknown`，
不要为了「填满词表」而勉强归类——那是本项目最贵的错误。

---

## 使用前提：逐条标注不是全量义务

对标 `live-annotation-schema.md` 的 `per_message` 语义：**只在真正看得出意图时才标**。

- 一句「哈哈」、一个表情、一句「在吗」，标 `acknowledge` 或 `unknown` 都可以，也可以不标
- 关系敏感意图（见下节）**必须**先过 F5，不是「标了就算」

## 一、12 类情绪

| key | 标签 | 判定标准 |
|-----|------|---------|
| `happy` | 开心 | 愉快、满足、开心或兴奋 |
| `confused` | 疑惑 | 不理解、好奇、疑问或困惑 |
| `angry` | 愤怒 | 真实生气、愤怒或强烈不满，**排除亲密玩笑式骂人** |
| `sad` | 难过 | 伤心、低落、悲伤 |
| `shy` | 害羞 | 羞涩、难为情或暧昧时不好意思 |
| `caring` | 关心 | 担心、关切或体贴对方 |
| `teasing` | 调侃 | 开玩笑、逗对方、玩梗或善意戏谑 |
| `calm` | 平静 | 客观陈述、平静中性交流，无明显情绪 |
| `annoyed` | 不耐烦 | 厌烦、想赶紧结束、不愿重复解释 |
| `surprised` | 惊讶 | 意外、吃惊、超出预期 |
| `disappointed` | 失落 | 期待落空、委屈、失望 |
| `unknown` | 难判断 | 无法判断主要情绪或以上均不适合 |

**两个容易出错的边界**：

- `angry` 排除「亲密玩笑式骂人」——「你是不是傻」在玩笑语境里是 `teasing`，不是 `angry`
- `calm` 经常被误读成「冷淡」。**平静 ≠ 冷淡**，`calm` 是「无明显情绪」，不是负向

**`probs` 的键必须用这张表。** 实时标注层历史示例里出现过「平淡/敷衍/关心」这套第三词表
（`live-annotation-schema.md` 文件 2 示例），那是词表未定义时期的遗留；`probs` 应为
「情绪类别 → 概率」，用上表 12 个 key。

## 二、36 类意图

> **`academic` 与本项目的既有口径直接对应**：`analysis-framework.md` A5 的「回应四类」
> 里，判定「投入」的标准之一是「给了对方没有的东西——新信息 / 反问 / 具体步骤 / 自己的经历；
> **讲技术属于此类**」。`academic` 就是它的词表化身——**话题正经不代表冷淡，也不自动等于调情**。

### 信息交换（12）

| key | 标签 | 判定标准 |
|-----|------|---------|
| `share` | 分享近况 | 主动讲自己的经历、活动或状态，主要是分享而非回答问题 |
| `answer` | 回答问题 | 回应前面的具体询问，主要目的是提供所问信息 |
| `inform` | 告知信息 | 通知事实、安排或进展，区别于分享个人感受和经历 |
| `ask` | 询问信息 | 获取事实、原因、安排或情况，**无需额外假定暧昧动机** |
| `clarify` | 确认理解 | 核对自己对前文的理解，询问是不是某个意思 |
| `explain` | 解释说明 | 澄清原因、误会或补充背景，让对方理解自己的话或行为 |
| `academic` | 学术讨论 | 讨论学习、学术、专业或技术问题（题目、论文、课程、代码、软件工具等），重点在交流知识本身；**话题正经不代表冷淡，也不自动等于调情** |
| `opinion` | 表达观点 | 陈述看法或评价，未明显要求对方赞同 |
| `agree` | 表示认同 | 赞同对方观点、感受或提议，不只是确认收到消息 |
| `disagree` | 表达异议 | 提出不同观点、反驳或纠正，**不等于拒绝关系** |
| `acknowledge` | 回应收到 | 简短确认已看到或听懂，例如嗯、好的；没有更明确的沟通目的 |
| `other` | 其他意图 | 能看出沟通目的，但不属于上述任何一类 |

### 话题维护（5）

| key | 标签 | 判定标准 |
|-----|------|---------|
| `continue` | 延续话题 | 接住前文或补充话头，主要在维持对话而非传达新信息 |
| `change` | 转移话题 | 将交流引向另一个话题，**不能仅因转移就推断逃避或拒绝** |
| `joke` | 玩笑逗趣 | 开玩笑、接梗或善意互损，主要为了有趣；**没有明显浪漫试探** |
| `ease` | 缓和气氛 | 缓解尴尬、冲突或紧张，玩笑在这里主要为了缓和关系 |
| `close` | 结束聊天 | 明确或含蓄表示本次对话先结束、自己要忙或休息 |

### 情绪支持（8）

| key | 标签 | 判定标准 |
|-----|------|---------|
| `vent` | 倾诉烦恼 | 表达困扰或抱怨以释放感受，**没有明显要求解决方案** |
| `comfort_seek` | 寻求安慰 | 通过表达脆弱或委屈，希望得到情绪支持，而不只是分享情况 |
| `validation` | 寻求认同 | 希望对方肯定自己的感受、看法或价值，区别于单纯表达观点 |
| `comfort` | 安慰支持 | 接住对方困扰、鼓励或给予支持，区别于寻求安慰 |
| `care` | 表达关心 | 关注对方状态或需要，主要是关怀，**不自动表示恋爱好感** |
| `help` | 请求帮助 | 希望对方提供具体建议、信息或实际帮助 |
| `advice` | 提供建议 | 主动提供解决办法或行动建议，不只是表达评价 |
| `praise` | 赞美欣赏 | 肯定对方特质或表现，**不自动等于调情** |

### 礼节（2）

| key | 标签 | 判定标准 |
|-----|------|---------|
| `thanks` | 表达感谢 | 感谢对方的回应、帮助或付出 |
| `apologize` | 道歉修复 | 承认不妥、致歉或尝试修复交流关系 |

### 关系动作（6）⚠️ 受 F5 约束

| key | 标签 | 判定标准 |
|-----|------|---------|
| `attention` | 寻求关注 | 希望对方多注意、回应或陪伴自己，**需要语境证据，普通分享不默认归此** |
| `interest` | 试探好感 | 间接探询对方是否在意自己或对自己有浪漫兴趣，**须有具体上下文支持** |
| `invite_hint` | 试探邀约 | 含蓄创造共同活动或见面的机会，尚未直接提出邀请；**单说"无聊"不够** |
| `invite` | 发出邀约 | 直接邀请对方见面、一起活动或协商具体安排 |
| `flirt` | 暧昧逗弄 | 用双关、亲昵或有浪漫意味的玩笑试探互动；**普通互损不默认暧昧，不等于同意进一步行为** |
| `affection` | 表达在意 | 表达想念、珍惜或对彼此关系的重视，**须有可见文本证据** |

### 边界与拒绝（2）

| key | 标签 | 判定标准 |
|-----|------|---------|
| `refuse` | 婉拒提议 | 委婉推辞当前提议或邀约，**不能扩大成拒绝恋爱或否定对方** |
| `boundary` | 表达边界 | 说明不愿、不能接受或要求停止的行为，**不把明确拒绝曲解为欲擒故纵** |

### 兜底（1）

| key | 标签 | 判定标准 |
|-----|------|---------|
| `unknown` | 难以判断 | 必要上下文缺失或存在无法消除的歧义，无法判断主要沟通意图 |

## 三、四类关系敏感意图的 F5 前置 ⚠️ 硬规矩

`attention` / `interest` / `invite_hint` / `flirt` 这四类**是关系判读的核心证据，也是本项目历史上判错最多的地方**。

**规矩：这四类必须先过 `analysis-framework.md` F5 的四轴判定，命中 < 2 轴不得作为证据进入任何下游模块。**

- 命中 ≥3 轴 → 可作证据，`evidence_level` 可达 `high`
- 命中 2 轴 → 可写入，`evidence_level` 上限 `medium`
- 命中 1 轴 → 只能写进 `observable_signals`，不得单独下结论
- 命中 0 轴 → 不计入

**为什么必须加这道闸**：这四类的 criteria 本身已经写了警告（「普通分享不默认归此」
「普通互损不默认暧昧」「单说无聊不够」），说明原表作者也意识到这里容易过度解读。
但 criteria 是**静态的**——它只能要求模型谨慎，不能给出量化门槛。F5 的四轴
（停驻性 / 复现性 / 指向性 / 悬置性）正好补上这个门槛。

**两项不可协商**：

1. **不得因为「这种话太常见」而默认判弱**——轴 4 无法判断时记「未定」而非「弱」
2. **不得绕开 F5**，用「意图词表里既然有这一类，说明它就是常见表达」来反向豁免

**已归档的实测教训**（写在 F5 正例锚点里）：一句「我最近好累」在中文日常里基准发生率极高，
单凭它判「她在示弱」是本框架最容易犯的错。

## 四、12 个时刻 kind（关键时刻轴）

与 36 意图的区别：**意图是「这一条在做什么」，时刻是「这个时间点值得跨片段记住」。**

| kind | 标签 | 判定标准 |
|------|------|---------|
| `boundary` | 拒绝 / 划清界限 | 明确提出保持距离、只做朋友、拒绝追求或停止联系的边界，**不是暂时忙碌** |
| `reopen` | 重新靠近 | 明确撤回先前的拒绝、重新允许接近或说明先前拒绝只是误会 |
| `invitation` | 邀约 | 提出具体邀约或相处计划 |
| `confirmation` | 确认安排 | 明确接受或确认此前的邀约、承诺或安排 |
| `cancellation` | 取消安排 | 明确取消、拒绝或改期已有的具体安排 |
| `care` | 关心 | 针对对方具体处境或需要提供关心、支持或帮助 |
| `preference` | 说出喜好 | 明确说出个人偏好、忌讳或重要习惯 |
| `disclosure` | 敞开心扉 | 主动分享重要个人经历、真实感受或脆弱处境 |
| `commitment` | 表达心意 | 明确表达喜欢、爱意或关系承诺，**不是普通夸奖** |
| `question` | 提问 | 向对方提出一个具体、尚待回应的问题 |
| `correction` | 澄清 | 明确澄清、纠正或解释前面某句话的意思 |
| `none` | — | 没有值得跨片段保留的明确事件，只有普通接话、模糊暗示或证据不够 |

**两级结构**（移植自上游 `Moments.tsx` 的 `MINOR` 集合）：

- **里程碑**：`boundary` / `reopen` / `invitation` / `confirmation` / `cancellation` / `care` / `disclosure` / `commitment`
- **次要**（`question` / `correction` / `preference`）：默认不进时间线主视图，避免把「关系里程碑」淹没在「今天问了道题」里

**三个 kind 与本项目的既有分析直接对应**：

- `boundary` → 本框架的**边界信号**，是 `scoring-rubrics.md` 里 `boundary_applied`（好感封顶）的触发源
- `reopen` → A3/A7 的**重新开门**动作。实测语料里这一类极重要：一次「自己重新开门」
  往往比十条热络消息更能说明关系状态
- `disclosure` → 与 F5 联用：`disclosure` 是「敞开心扉」的**事件级**判定，F5 是**语句级**的强度判定，
  两者不可互相替代——一个 `disclosure` 事件里可能全是 0 轴的客套话

**状态与置信度**（沿用上游语义）：

- `status` 三态：`active`（仍有效）/ `resolved`（已被后续事件消解）/ `uncertain`（存疑）
- **confidence < 0.65 的时刻不写入**（上游 `collectEvents()` 的门槛）。宁可漏，不可凑

## 五、使用纪律汇总

1. **词表是推荐值域**，消费方容忍表外值
2. **`unknown` / `other` 是合法结果**，不是失败
3. **四类关系敏感意图强制过 F5**，命中 < 2 轴不得作为证据
4. **`probs` 用 12 情绪 key**，不用遗留的第三套词表
5. **次要时刻不进主视图**（`question` / `correction` / `preference`）
6. **时刻 confidence < 0.65 不写入**
7. 逐条标注**不是全量义务**——只看得出时才标，其余留空即 `pending`

## 六、与下游模块的接口
